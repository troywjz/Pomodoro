# 协作与上下文管理

用户已授权采用稳定模块责任、短任务session、有限并行和按变更使用Worktree。当前状态见[项目状态](../project-state.md)，旧角色研究见[归档](../archive/role-studies/README.md)。

| 责任分组 | 唯一主责范围 |
| --- | --- |
| Lead/集成协调 | 范围、依赖、公共契约、构建入口、集成与验收 |
| 产品与交互设计 | 需求/指标口径、AC、Figma与视觉交互；专业角色按任务安排 |
| 计时与应用流程 | 纯计时、命令/快照、应用协调器、保存回执、恢复业务和退出 |

| 本地数据 | JSONL/Repository、追加与迁移、自动备份、导出/清理及查询；v0.1 SQLite 仅为迁移源 |

| 独立验证 | 指定提交/原型的审查、实机与资源验收 |

统计作为特性任务：产品定义含义，应用层组织，数据层查询。恢复业务归应用流程，系统事件采集归平台。公共协议在[契约入口](../contracts/README.md)统一维护，研究稿按需参考。

## 生命周期

1. Ready：commit、批准版本、接口、允许路径、验证、依赖和停止条件齐备。
2. Doing：新session只读任务说明和直接依赖；同一工作树只有一个写入session。
3. Review：交提交、差异和真实验证；独立审查先看标准和实际产物，再按需查作者过程。
4. Integrated/Accepted：用户批准后合并，执行集成回归；研究产出与功能接受分别登记。
5. 交接完成后归档session和工作树，下一独立任务使用新上下文。

开发从3个实现任务并行起步，按等待/返工/审查积压调整。设计阶段主要激活需求澄清、原型收尾与独立评审。共享Figma/Notion页面、schema和构建文件有明确写入者。

使用[任务模板](../templates/task-brief.md)和[交接模板](../templates/delivery.md)。环境/UI诊断独立成运维任务。用户调整需求后记录Issue/决策，Lead只同步受影响版本。

Lead按里程碑读取项目状态和必要决策接续。组织理由见[已采纳方案](context-and-parallelism-proposal.md)。
